How it fits together

The canvas saves a workflow as JSON. The API walks that graph node by node, stores every output, and streams progress back over Server-Sent Events.

What happens when a flow runs

  1. 01

    Draw it

    Nodes and connections live on a React Flow canvas and save as plain JSON, so a workflow is just data.

  2. 02

    Walk the graph

    The runner does a pre-order traversal from the trigger, running one node at a time.

  3. 03

    Chain the outputs

    Each node’s output is saved to the Responses table, so later nodes can use what earlier ones produced, like an AI-written message going out on Telegram.

  4. 04

    Pause on a webhook

    A webhook node stops the run and hands out a callback URL. When that URL is hit, the run resumes at the right node with everything it had before.

  5. 05

    Watch it live

    Every step streams to the browser over Server-Sent Events, so you see the run as it happens.

The tricky part

Pausing. A normal run is just a loop, but a webhook node means a run can stop for minutes or hours and has to pick up exactly where it left off, with every earlier output still available.

Saving every node’s output to the database, instead of keeping it in memory, is what makes resuming possible: the run doesn’t need to still be alive to continue.

What I’d build next

  • Retries per node, so one flaky API call doesn’t fail the whole run.
  • A queue-based worker system, so runs don’t live inside the API process.
  • Validation schemas per node type, so bad config is caught before a run starts.
