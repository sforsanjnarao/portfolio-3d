Case study · trading engine

Velocity

A real-time crypto perpetuals exchange I built on my own. Live BTC, ETH and SOL prices, long and short positions with up to 100× leverage, and an in-memory engine that checks every open position on every price tick.

How it fits together

Four services talk through Redis Streams. Nothing waits on the database: the engine keeps state in memory and writes to Postgres in batches.

What happens to an order

  1. 01

    You place an order

    The web app sends it to the HTTP server, which checks your JWT cookie and validates the body with Zod.

  2. 02

    It goes onto a stream

    The server adds it to the trading-engine Redis Stream and waits for the reply.

  3. 03

    The engine fills it

    Longs open at the ask and shorts at the bid, using the latest price from Backpack. Margin, leverage and price are all BigInt with 8 decimals, so there is no floating point anywhere near the money.

  4. 04

    Every tick checks every position

    Each new bid/ask from the price poller runs through all open positions: liquidation first, then take-profit, then stop-loss. Positions close at the opposite side of the book.

  5. 05

    The result comes back

    The engine writes the outcome to callback_queue, the HTTP server reads it and answers the request, and Postgres gets the change in the next batch write.

What broke

I started with plain Redis pub/sub for order events. Under load, if the engine restarted mid-process, in-flight orders just vanished, because pub/sub doesn’t keep anything for a listener that isn’t there.

Moving to Redis Streams gave every event a place to live instead of a message that disappears if nobody is listening. That bug taught me more about how distributed systems fail than anything else I’ve built.

What I’d build next

  • Consumer groups with acknowledgements, so the engine can replay anything it missed while it was down.
  • A proper order book with limit orders, not just market fills against the best bid and ask.
  • Load tests that put real numbers on how many positions one engine can check per tick.
